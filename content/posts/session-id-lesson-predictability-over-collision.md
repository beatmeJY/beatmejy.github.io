몇 년 전, 토이 프로젝트에서 세션 키를 직접 생성해야 했던 적이 있다. 그때 나는 "UUID도 이론상 중복될 수 있다"는 사실이 유독 마음에 걸렸고, 충돌 확률을 조금이라도 더 낮춰보겠다며 밀리세컨드 시간을 키에 섞어 넣는 방법을 며칠 동안 붙잡고 있었다. 계산 결과가 잘 나와서 나름 뿌듯해했던 기억이 난다.

4년차가 된 지금 그 글을 다시 꺼내 읽어보니, 계산은 틀리지 않았는데 **애초에 잘못된 질문에 답하고 있었다**는 걸 깨달았다. 그때의 실험과, 지금 보이는 게 뭐가 다른지 정리해본다.

---

## 그때 던졌던 질문: "충돌 확률을 어떻게 더 낮출까"

당시 조건은 이랬다.

- 세션은 최대 24시간 유지
- 초당 10,000건의 세션 키 생성
- 비교 기준은 UUID의 16진수 32자리(하이픈 제외)

UUID(v4)는 초당 100만 건씩 100년을 생성해도 충돌 확률이 0.00009% 수준이라는 걸 알고 있었다. 그런데도 "확률이 0이 아니다"는 사실 자체가 신경 쓰여서, 이걸 더 낮출 방법을 찾아 나섰다.

### 방법 A: UUID만 사용

```java
import java.util.UUID;

public String createSessionId() {
    return UUID.randomUUID().toString();
}
```

- 전체 경우의 수: `16^32 = 340,282,366,920,938,463,463,374,607,431,768,211,456`
- 하루 생성량(r): `10,000 × 60 × 60 × 24 = 864,000,000`건
- 하루 중 충돌 확률: 약 `1.1 × 10⁻²¹`%

### 방법 B: 밀리세컨드 + UUID

키 앞 8자리를 "하루 중 몇 번째 밀리세컨드인지"로 채우고, 나머지를 UUID의 랜덤 값으로 채웠다.

```java
import java.util.UUID;

private static final long MILLISECOND_BY_DAY = 86_400_000L;

public String createSessionId() {
    long todayMillisecond = System.currentTimeMillis() % MILLISECOND_BY_DAY;
    String millisecond = String.format("%08d", todayMillisecond);

    UUID uuid = UUID.randomUUID();
    String randomPart = uuid.toString().substring(8);

    return millisecond + randomPart;
}
```

```
42120209-cdb2-4e75-bcdb-3ea7b6fb0673
42139071-6d91-45c4-98bd-6c5029cb9556
42144408-ee75-40d9-843f-da93492daa58
```

같은 밀리세컨드 안에서만 충돌이 가능하므로 비교 대상은 나머지 16진수 24자리뿐이다.

- 나머지 24자리 경우의 수: `16^24 = 79,228,162,514,264,337,593,543,950,336`
- 같은 밀리세컨드 안에 생성되는 키 개수: 약 10건
- 하루 중 충돌 확률: 약 `5.7 × 10⁻²⁸`%

밀리세컨드를 섞은 쪽이 UUID만 쓴 것보다 **약 200만 배 낮은 충돌 확률**을 보였다. 그때는 이 숫자를 보고 "역시 시간을 넣는 게 맞았다"고 결론을 내렸다.

## 지금 돌아보면 놓친 것

지금 다시 이 숫자를 보면, 애초에 비교 자체가 무의미했다는 게 먼저 보인다.

`10⁻²¹%`는 이미 "사실상 절대 일어나지 않는다"고 봐도 되는 수준이다. 이걸 `10⁻²⁸%`로 더 낮춰봤자, 둘 다 인간이 체감할 수 있는 확률 범위 밖에 있다는 사실은 바뀌지 않는다. 그때의 나는 "더 작은 숫자 = 더 나은 설계"라고 단순하게 생각했지, **애초에 이 숫자를 줄이는 게 실제로 의미가 있는 개선인지**는 따져보지 않았다.

그리고 더 결정적으로, 세션 키처럼 보안이 중요한 값에서 진짜 신경 써야 할 건 충돌 방지가 아니라 **예측 불가능성**이다. 공격자가 다른 사용자의 세션 키를 우연히 얻어걸리는 상황이 아니라, 유추하거나 추측해서 알아낼 수 있는지가 문제다. 그런데 밀리세컨드를 키에 넣는 순간, "이 세션이 정확히 언제 만들어졌는지"라는 정보를 키 자체에 새겨 넣은 셈이 된다. 나머지 24자리의 경우의 수는 여전히 막대하지만, 완전한 무작위 128비트보다 구조적으로 유추 가능한 요소가 늘어난 건 사실이다.

## UUID v1과 v4, 그리고 뒤늦게 이해한 이유

그때 글을 쓰면서도 UUID v1이 이미 현재 시간(과 MAC 주소)을 조합해서 키를 만든다는 걸 알고 있었다. 그런데도 실무에서는 압도적으로 v4가 더 많이 쓰인다는 사실도 알고 있었으면서, 그 이유를 깊게 생각해보지 않고 넘어갔었다.

지금 생각해보면 이유는 명확하다. v1이 밀려난 건 충돌 확률이 v4보다 나빠서가 아니다. **MAC 주소와 타임스탬프라는, 외부에서 유추 가능한 정보를 식별자 안에 그대로 노출시킨다는 게 문제였다.** 세션 토큰처럼 보안이 걸린 값에 이런 유추 가능한 데이터를 섞는 건, 충돌 확률을 아무리 낮춰도 상쇄되지 않는 리스크다. 그리고 내가 몇 년 전에 했던 "밀리세컨드 섞기" 실험은, 정확히 v1이 v4로 대체된 것과 같은 방향의 실수를 반대로 다시 저지른 셈이었다.

---

## 지금이라면 이렇게 했을 것

- 세션 키처럼 보안이 걸린 식별자는 **처음부터 UUID v4(혹은 그에 준하는 완전 무작위 값)를 그대로 쓴다.** 충돌 확률을 더 낮추겠다고 예측 가능한 요소를 섞지 않는다.
- 만약 정말로 순서 보장이나 인덱싱 효율처럼 다른 이유로 시간 정보를 식별자에 포함시켜야 한다면, 그건 주문 번호나 로그 ID처럼 **보안 민감도가 낮은 식별자에 한해서만** 고려한다.
- 어떤 지표(이번 경우 충돌 확률)를 개선하기 전에, 그 지표가 이미 무시해도 되는 수준인지, 그리고 그걸 개선하는 대가로 다른 무엇을 내주고 있는지부터 확인한다.

---

## 배운 점

- 계산이 정확하다고 해서 그 계산이 답하고 있는 질문 자체가 옳은 건 아니다. 그때 나는 "충돌 확률을 어떻게 낮출까"라는 질문에 열심히 답했지만, 정작 물어봤어야 할 질문은 "세션 키에서 진짜 중요한 게 뭘까"였다.
- 널리 쓰이는 표준(UUID v4)이 왜 그 형태로 자리 잡았는지를 그 표준이 대체한 이전 버전(v1)과 비교해서 이해하면, 내가 지금 만들고 있는 게 이미 누군가 겪고 버린 실수를 반복하는 건 아닌지 미리 알아챌 수 있다.
- "더 작은 숫자"나 "더 정교한 계산"이 항상 "더 나은 설계"를 의미하지는 않는다. 무엇을 최적화하고 있는지부터 다시 물어야 한다.
