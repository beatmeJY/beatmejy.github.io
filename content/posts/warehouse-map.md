## 들어가며

WMS를 만들다 보면 "로케이션"은 결국 문자열 하나로 수렴한다. `1-1-1`, `2-14-3` 같은 ID다.
이 값은 시스템 입장에서는 완벽하다. 유니크하고, 인덱스가 걸리고, 조인도 잘 된다.

문제는 이 값을 받아들이는 쪽이 사람이라는 것이었다.

이 글은 3,800개가 넘는 격자 셀 위에 창고를 다시 그리고, 그 위에 재고를 얹고,
관리자가 그 판을 직접 편집할 수 있게 만들기까지의 설계 기록이다.

작업자가 `1-1-1`을 해석하는 대신 위치를 눈으로 보게 하는 것,
그리고 **그 위에서 동선까지 계산하는 것**이 목표였다.

![포천 센터 1동 1층 — 행거 열이 통로를 사이에 두고 좌우로 깔려 있다](/images/map_main_image.png)

## 1. 무엇이 문제였나

### 1-1. "어디에 있는지"는 알아도 "어떻게 가는지"는 몰랐다

기존 화면에서 상품을 검색하면 결과는 이런 식이었다.

```
상품번호 30219  →  행거 3-12-2
```

그런데 현장 얘기를 듣다 보니 신입 작업자에게 이 값은 아무 의미가 없었다.
`3-12-2`가 입구에서 가까운지 먼지, 왼쪽 통로인지 오른쪽 통로인지, 2층인지 1층인지가
ID 안에 들어 있긴 한데 **그 규칙을 아는 사람만 읽을 수 있었다.**

결국 현장에서는 이런 일이 반복됐다.

- 숙련자가 옆에서 "아 그건 저기 안쪽 두 번째 열" 하고 통역해준다
- 통역해줄 사람이 없으면 직접 돌아다니면서 찾는다
- 그 시간이 고스란히 피킹 리드타임이 된다

시스템은 정답을 알고 있는데, 그 정답이 사람에게 전달되지 않고 있었다.

### 1-2. 로케이션 체계가 설비마다 달랐다

더 귀찮은 문제는 창고 안 설비가 한 종류가 아니라는 점이었다.

| 설비 | 무엇이 놓이나 | ID 체계 | 실제 값 |
|------|--------------|---------|---------|
| 행거(HANGER) | 상품(옷) | 층-열-번호 | `11-50-1` |
| 경량 렉(RACK_HANGER) | 상품 | 블록-번호-층 | `RC-12-3` |
| 렉(RACK) | 팔레트 패키지 | 층-열-번호 | — |
| 존(ZONE) | 여러 설비를 묶은 구역 | 단일 ID | — |

똑같이 하이픈 세 토막인데 **자리마다 의미가 달랐다.** 행거는 첫 자리가 층이고,
경량 렉은 첫 자리가 `RA`/`RB`/`RC` 블록 문자에 마지막 자리가 층이다.
이걸 화면마다 다른 조건문으로 처리하고 있었고, 새 설비가 들어올 때마다 분기가 늘어났다.

### 1-3. 창고는 고정된 도형이 아니었다

그리고 가장 뼈아픈 제약이 있었다. 창고 레이아웃은 계속 바뀐다.
통로 하나를 넓히거나, 랙 한 줄을 통째로 들어내거나, 짧은 시즌마다 존을 재배치한다.

"한 번 그려놓고 끝"인 정적 이미지로는 한 달도 못 버틴다는 뜻이었다.

## 2. 어떻게 생각했나

정리하면 요구사항은 세 개였다.

1. 공간을 **눈에 보이게** 만들 것
2. 설비마다 다른 ID 체계를 **한 곳에서** 흡수할 것
3. 레이아웃 변경을 **관리자가 직접** 할 수 있을 것

여기에 회사가 요구한 건 아니지만 내가 처음부터 목표로 잡고 있던 게 하나 더 있었다.

4. **경로 탐색**까지 붙여서 작업자의 동선을 계산할 것

사실 맵을 만들자고 한 계기의 절반은 4번이었다.
"어디에 있는지"를 보여주는 데서 끝내면 작업자는 여전히 자기가 짠 순서대로 돌아다닌다.
1-1에서 적은 "직접 돌아다니면서 찾는다"를 진짜로 없애려면 순서를 계산해줘야 했다.

그래서 화면부터 짜지 않고 데이터 정의를 먼저 했다.
**창고를 좌표와 방향을 가진 격자로 두면** 같은 데이터가 화면에도 쓰이고 BFS에도 쓰인다.
반대로 보여주기 편한 모양으로 먼저 만들어두면 동선을 계산할 때 데이터를 다시 만들어야 한다.
앞으로 나오는 결정 중 상당수는 이 4번을 남겨두려고 고른 것이다.

미리 밝혀두면 이 글은 그 판을 깔기까지다. 탐색 자체는 붙이지 못했고, 다음 편의 몫이다.

정의는 이렇게 잡았다.

- **노드** = 창고 격자의 셀 하나 `(warehouseId, floor, pointX, pointY)`
- **엣지** = 그 셀에서 이동 또는 접근이 허용된 방향 (둘의 구분은 4절과 9절에서 다룬다)

## 3. 설계 1 — 공간과 설비를 분리한다

코드를 쓰기 전에 테이블을 먼저 그렸다. 나는 시작 전 테이블 설계가 제일 재밌다.
나중에 어긋난 것도 있지만, 공간과 설비를 두 장으로 나누는 것만은 시작 전에 정했다.

처음 그린 안은 테이블 한 장이었다. `cn_wms_map`에 `object_id` 컬럼을 하나 두고
"이 셀에 놓인 설비"를 적는 식이다. 셀과 설비가 1:1이면 이게 제일 단순하다.

그 1:1이 성립하는지 실제 설비를 하나씩 대보다가 접었다.
경량 렉은 같은 자리에 2층, 3층이 쌓여서 한 셀에 ID가 여러 개 필요했고,
존은 반대로 하나의 ID가 여러 셀에 걸쳐 있었다.

그래서 테이블을 두 장으로 나눠서 시작했다.

```
cn_wms_map              cn_wms_map_location
(격자 셀 = 공간)   1:N   (셀에 놓인 설비)
```

```java
@Table(name = "cn_wms_map")
public class WmsMapEntity {
    private Long id;
    private Long warehouseId;
    private EMapType type;      // FLOOR, WALL, DOOR, STAIRS, RACK, HANGER, ZONE...
    private Integer pointX;
    private Integer pointY;
    private Integer floor;
    private Integer availableDir;   // ← 상호 작용 비트 (이 글의 주인공)
}
```

공간은 공간대로, 그 위에 뭐가 놓였는지는 따로 두니까
"통로만 늘리기"나 "설비만 다시 꽂기" 같은 편집이 서로를 건드리지 않게 됐다.

응답 DTO도 이 구조를 그대로 반영한다. 셀 하나가 `mappings` 배열을 갖는다.

```java
WmsMapLocationMappingResDTO dto = result.computeIfAbsent(mapId, id ->
    new WmsMapLocationMappingResDTO(id, pointX, pointY, type, availableDir)
);

if (findDTO.getMapLocationId() != null) {
    dto.addMapping(new WmsMapLocationSimpleResDTO(...));
}
```

셀 단위로 `computeIfAbsent`를 돌려서, 조인 결과로 터진 행들을 셀 하나당 하나의 객체로 접는다.
맵 화면은 셀과 매핑을 항상 같이 그리니, 클라이언트가 두 목록을 받아서 맞춰 붙이게 두지 않았다.
한 번에 내려주고, 셀마다 `mappings`가 들어 있는 모양으로 맞춘 것이다.

## 4. 설계 2 — 방향을 비트 하나에 담는다

### 왜 엣지 테이블을 안 만들었나

처음엔 정석대로 `cn_wms_map_edge` 테이블을 생각했다.
`from_map_id`, `to_map_id`, `cost` 같은 구조다.

조회 비용이 걱정돼서 접은 건 아니다. 한 층 2,000셀에 엣지 8,000행쯤은 인덱스만 있으면 되는 규모다.
걸린 건 삽입 쪽이었다. 행 하나를 끼워 넣는 기능을 어떻게 만들지 적어보다가
그 줄에 걸린 엣지를 **전부 다시 계산해야 한다**는 걸 알았다.
좌표를 미는 UPDATE 한 방으로 끝날 일에 엣지를 지우고 다시 만드는 작업이 따라붙는다.

그런데 격자에서 이웃은 `(x±1, y)`, `(x, y±1)`로 **좌표가 곧 답이다.**
자명하게 유도되는 관계를 테이블에 중복 저장하고, 레이아웃이 바뀔 때마다 그 중복을 동기화하는 셈이었다.

그래서 방향을 **셀 자신의 속성**으로 뒤집어봤다.
"이 셀에서 나갈 수 있는 방향"만 알면 인접 리스트는 필요할 때 만들면 되고,
좌표를 밀어도 각 셀이 자기 값을 그대로 들고 가기 때문에 다시 계산할 게 없었다.

### Bit Flag

방향은 네 개, 값은 2의 거듭제곱으로 잡았다.

| 방향 | 비트 | 2진수 |
|------|------|-------|
| UP | 1 | `0001` |
| RIGHT | 2 | `0010` |
| DOWN | 4 | `0100` |
| LEFT | 8 | `1000` |

합치면 0~15로 모든 조합이 표현된다. 컬럼은 `available_dir` 하나, 타입은 Integer.

- `15` = 사방 통행 (새로 만드는 바닥 셀의 기본값)
- `0` = 완전 차단 (벽 등)
- `6` = RIGHT + DOWN
- `2` = 오른쪽만 열림 (통로가 오른쪽에 있는 행거 셀)

```java
public enum EDirection {
    UP(1), RIGHT(2), DOWN(4), LEFT(8);

    public boolean isAvailable(int availableDir) {
        return (availableDir & bit) != 0;
    }
}
```

### "벽"과 "접근 방향"은 다른 개념이다

통행 불가를 `EMapType.WALL`로만 두면 랙을 설명할 수 없다.
랙이 놓인 셀은 벽이 아니다. 물건을 집을 수 있다. 다만 **한쪽 통로에서만** 집을 수 있다.
그걸 타입으로 밀면 `RACK_LEFT_ACCESSIBLE` 같은 값이 설비마다 늘어난다.

그래서 타입은 "무엇인가", `availableDir`은 "어떻게 닿을 수 있나"로 나눴다.
타입 enum은 9개로 두고, 접근은 숫자 하나로 조합한다.

## 5. 설계 3 — 격자를 나중에 고칠 수 있게

"레이아웃은 계속 바뀐다"는 제약에 대한 답이다.

행/열 삽입은 **기존 좌표를 밀어내고 빈 줄을 채우는** 방식으로 처리했다.

```java
@Modifying
@Query("""
    UPDATE WmsMapEntity m SET m.pointX = m.pointX + :shift
    WHERE m.warehouseId = :warehouseId AND m.floor = :floor AND m.pointX >= :targetX
""")
void shiftRight(...);
```

`shiftRight`, `shiftDown`, `shiftLeft`, `shiftUp` 네 개를 JPQL 벌크 업데이트로 만들었다.
엔티티를 전부 읽어서 루프 도는 대신 SQL 한 방으로 좌표를 옮긴다.

삽입 로직은 이렇게 흐른다.

```java
Integer targetX = RIGHT.equals(direction) ? entity.getPointX() + 1 : entity.getPointX();
Integer targetY = DOWN.equals(direction)  ? entity.getPointY() + 1 : entity.getPointY();

switch (direction) {
    case LEFT, RIGHT -> {
        jpaRepository.shiftRight(warehouseId, floor, targetX, count);
        lineMaxIndex = getMaxPointY(warehouseId, floor);   // 새 열의 길이
    }
    case UP, DOWN -> {
        jpaRepository.shiftDown(warehouseId, floor, targetY, count);
        lineMaxIndex = getMaxPointX(warehouseId, floor);   // 새 행의 길이
    }
}
```

LEFT/RIGHT는 같은 `shiftRight`를 쓰되 기준 좌표만 `+1` 차이를 준다.
"왼쪽에 삽입"은 결국 "자기 자리부터 밀기"이고, "오른쪽에 삽입"은 "다음 자리부터 밀기"라서
분기 두 개가 아니라 **오프셋 하나**로 끝난다.

새로 생기는 셀은 전부 `FLOOR` 타입에 `availableDir = 15`로 채운다.
빈 통로로 깔아놓고 관리자가 그 위에 설비를 얹는 순서다.

### 이 방식의 약점 — 동시 편집

좌표를 읽고, 밀고, 새 셀을 넣는 사이는 원자적이지 않다.
관리자 두 명이 같은 층을 동시에 편집하면 어떻게 되는지를 정해둬야 했다.

**정합성은 DB에 맡겼다.** `cn_wms_map`의 `(warehouse_id, floor, point_x, point_y)`에 유일 제약을 걸어서,
좌표가 겹친 셀은 애초에 들어가지 못하게 했다.
애플리케이션이 순서를 제대로 지켰는지와 무관하게 겹침은 DB가 거부한다.
격자에서 좌표는 사실상 자연키라서, 그 판단을 코드 쪽에 두고 싶지 않았다.

**대신 층 단위 락은 걸지 않았다.** 그래서 거의 동시에 삽입을 누르면
좌표가 겹치는 순간 유일 제약이 걸려서 한쪽이 실패한다.
순서에 따라서는 줄이 두 번 밀려 의도하지 않은 빈 줄이 남기도 한다.
데이터가 깨지지는 않지만, 관리자에게는 "맵 생성에 실패하였습니다"라는 문구만 간다.
왜 실패했는지, 다시 누르면 되는지 알 수 없다.
맵을 편집하는 사람이 사실상 한 명이라 충돌 자체가 드물었고,
데이터가 깨지지 않는 선까지만 막아두고 넘어갔다.

지금 다시 한다면 두 곳을 손볼 것 같다.
하나는 유일 제약 위반을 잡아서 "다른 관리자가 같은 층을 수정했습니다"로 내려주는 것이다.
다른 하나는 라인 삭제다. 매핑이 걸려 있으면 삭제를 막는데,
그 확인과 실제 삭제 사이에 다른 요청이 같은 셀에 매핑을 넣을 수 있다.
막으려면 확인과 삭제를 한 번에 한 요청만 지나가게 해야 한다.
트랜잭션은 부분 반영은 막아주지만 동시 요청은 막아주지 않는다.

## 6. 설계 4 — 설비마다 다른 ID 체계를 enum이 흡수한다

1-2에서 이야기한 "자릿수 의미가 다른 문제"는 타입별 `switch`로 처리할 수도 있었다.
설비가 네 종류뿐이라 `if (type == HANGER) ... else if (type == RACK_HANGER) ...`로도 돌아간다.
그런데 기존 화면들이 이미 그 분기를 각자 들고 있었고,
설비가 하나 늘 때 어느 화면을 같이 고쳐야 하는지 아는 사람이 개발자들뿐이었다.

타입마다 다른 건 결국 "어느 자리가 움직이는가"뿐이라서, 그 자리를 enum에 상수로 넣었다.

```java
public enum EObjectType {
    RACK_HANGER("경량 렉", 1, 2),   // 증가 인덱스 1, 층 인덱스 2
    RACK       ("렉",     2, 0),
    HANGER     ("행거",   2, 0),
    ZONE       ("존",    -1, -1);   // 단일 매핑

    public boolean isBulkGeneratable() { return increaseIndex >= 0; }
    public boolean hasFloor()          { return floorIndex >= 0; }
}
```

`-1`을 "해당 없음"으로 썼다. 호출부에서 `increaseIndex >= 0`을 그대로 비교하면
이 조건이 무슨 뜻인지 매번 enum까지 올라가서 봐야 하니 `isBulkGeneratable()` / `hasFloor()`로 감쌌다.

이렇게 두니 **ID 생성 로직**에서 타입 분기가 사라졌다.

```java
private List<String> generateObjectIds(String baseId, int count, int floorCount, EObjectType type) {
    if (!type.isBulkGeneratable()) return List.of(baseId);   // ZONE

    String[] baseParts = baseId.split("-");
    int incIdx   = type.getIncreaseIndex();
    int floorIdx = type.getFloorIndex();
    ...
}
```

관리자는 시작 ID와 층 개수만 입력하면 된다.
경량 렉 `RC-12-3`이면 가운데 자리가 셀마다 증가하고 마지막 자리가 층으로 펼쳐지고,
행거 `11-50-1`이면 마지막 자리가 셀마다 증가하고 **첫 자리가 층으로 펼쳐진다.**
어느 자리가 움직이는지는 enum만 알고, 화면은 그 차이를 모른다.

실제로 한 셀에 행거 매핑 `11-1-1`과 `12-1-1`이 같이 걸려 있다. 층 2개로 펼친 결과다.
매핑이 걸린 셀 1,474개 중 1,344개가 이렇게 2개씩을 들고 있다.

존은 `isBulkGeneratable()`이 false라 ID를 하나만 돌려주고, 그 하나가 선택된 모든 셀에 매핑된다.
존만 규칙이 다른 게 계속 신경 쓰였는데, `-1`로 빼는 것보다 깔끔한 방법은 아직 못 찾았다.

## 7. 프론트 — 관리자가 3,800개 셀을 감당하게 만들기

나는 백엔드 개발자다. 이 화면은 붙일 사람이 없어서 직접 붙였고,
그래서 여기 적는 것도 프론트 기술 이야기는 아니다.

다만 짚고 갈 이유는 있다. 백엔드 설계가 아무리 깔끔해도 관리자가 셀 3,800개를
하나씩 클릭해야 한다면 그 기능은 쓰이지 않는다. 실제로 **행거 2,746개, 경량 렉 528개**,
합쳐서 3,274개가 매핑돼 있다. 손으로 찍는 건 불가능하다.

두 가지만 자세히 적는다. **데이터 규모 때문에 자료구조를 골라야 했던 대목**과
**4절에서 정한 비트 하나가 화면까지 그대로 내려간 대목**이다. 나머지는 뒤에 한 번에 몰았다.

### 7-1. 선택을 자료구조로 정하기

선택 상태를 전역 `Set`으로 들고 시작했다.

```js
let selectedCells = new Set();
let lastClickCell = null;
```

배열이 아니라 `Set`인 이유는 단순하다.
토글(선택/해제)이 기본 동작이라 `has`, `add`, `delete`가 O(1)이어야 했고,
범위 선택에서 겹치는 셀이 중복으로 들어가는 걸 자료구조 차원에서 막고 싶었다.
범위를 세 번 겹쳐 끌어도 일괄 API에 나가는 `mapIdList`는 중복이 없다.

**Shift 범위 선택**은 엑셀에서 쓰는 감각을 그대로 가져왔다.

```js
function selectRange(a, b) {
  const minX = Math.min(a.pointX, b.pointX);
  const maxX = Math.max(a.pointX, b.pointX);
  const minY = Math.min(a.pointY, b.pointY);
  const maxY = Math.max(a.pointY, b.pointY);

  for (let x = minX; x <= maxX; x++) {
    for (let y = minY; y <= maxY; y++) {
      const el = $layer.find(`[data-x="${x}"][data-y="${y}"]`)[0];
      const id = el?.dataset?.id;
      if (el && id && id !== "null") {
        selectedCells.add(Number(id));
        el.classList.add("selected");
      }
    }
  }
  updateSelectedCount();
}
```

`min`/`max`로 정규화한 건 시작점에서 끝점까지 그냥 `for`를 돌리면
오른쪽 아래로 끌 때만 동작하기 때문이다. 관리자는 어느 방향으로 끌든 같은 사각형을 기대한다.

그리고 선택 개수를 화면에 크게 박았다.
일괄 작업은 "몇 개를 건드리는지 모르는 상태"가 가장 위험하다.
실수로 300개를 선택해두고 "유형 수정"을 누르는 상황을 숫자 하나로 막았다.


### 7-2. 클릭하지 않고도 셀 정보를 읽게

호버 툴팁에는 좌표·유형과 함께 **상호작용 방향을 화살표로** 그렸다.

```js
const dirUI = `
  <div class="hover-dir-box">
    <span class="hover-dir ${availableDir & DIR.LEFT  ? "active" : ""}">←</span>
    <span class="hover-dir ${availableDir & DIR.UP    ? "active" : ""}">↑</span>
    <span class="hover-dir ${availableDir & DIR.DOWN  ? "active" : ""}">↓</span>
    <span class="hover-dir ${availableDir & DIR.RIGHT ? "active" : ""}">→</span>
  </div>
`;
```

`availableDir & DIR.LEFT`가 그대로 CSS 클래스로 이어진다.
관리자에게 `6`이라는 숫자를 보여주는 대신 **켜진 화살표**를 보여준다.
비트 연산을 아는 건 개발자지 관리자가 아니다.

  <img src="/images/map_direction_modify.png" alt="행거 방향 수정" />

### 7-3. 그 외에 화면을 쓸 수 있게 만들며 한 일

- 행/열 삽입·삭제는 우클릭 메뉴로 뒀다. 기준 셀이 이미 정해진 상태로 시작한다.
- 셀 크기는 **모든 층의 최대 컬럼 수**로 맞춘다. 층마다 따로 계산하면 층을 바꿀 때 축척이 달라 보인다.
- 층은 탭으로 갈아끼우지 않고 겹쳤다. 2층을 볼 때 1층 윤곽이 비쳐서 계단 위치를 맞출 수 있다.
- 일괄 수정 뒤에는 현재 층만 다시 그리고, 선택은 유지한다. 방향을 바꾼 뒤 같은 선택으로 유형까지 바꾸는 흐름이 자주 나왔다.


### 7-4. 데이터가 곧 벽이 되는 CSS

**프론트에서 개인적으로 가장 마음에 드는 부분**이다.
`availableDir` 값을 그대로 클래스 이름에 붙였다.

```js
if (cell.availableDir) $cell.addClass(`dir-mask-${cell.availableDir}`);
```

그리고 CSS에서 **막힌 변에만** inset box-shadow로 벽선을 그린다.

```css
/* 2 = RIGHT만 열림 → 위/아래/왼쪽에 벽 */
.dir-mask-2 {
  box-shadow:
    inset 0 var(--wall-size) 0 0 var(--wall-color),                 /* top */
    inset 0 calc(-1 * var(--wall-size)) 0 0 var(--wall-color),      /* bottom */
    inset var(--wall-size) 0 0 0 var(--wall-color);                 /* left */
}

/* 15 = 사방 통행 → 벽 없음 */
.dir-mask-15 { box-shadow: none; }
```

여기에 하나를 더 얹었다. 셀의 `::before`(설비 아이콘)를 **열린 방향으로 회전**시킨다.

```css
.dir-mask-1::before  { transform: rotate(180deg); }   /* UP */
.dir-mask-2::before  { transform: rotate(-90deg); }   /* RIGHT */
.dir-mask-4::before  { transform: rotate(0deg); }     /* DOWN */
.dir-mask-8::before  { transform: rotate(90deg); }    /* LEFT */
.dir-mask-3::before  { transform: rotate(-135deg); }  /* UP+RIGHT → 대각선 */
```

두 방향이 열려 있으면 그 사이 각도로 돌린다. `3`(UP+RIGHT)이면 -135도.
결과적으로 **설비 아이콘이 통로 쪽을 바라본다.**
관리자는 맵을 보는 것만으로 "이 행거는 오른쪽 통로에서 집는 거구나"를 읽을 수 있다.

DB의 정수 하나가 JS에서 클래스 이름이 되고, CSS에서 벽과 아이콘 각도가 된다.
중간에 변환 로직이 한 줄도 없다. 이게 비트 마스크를 쓴 진짜 내 목적이었다.

## 8. 조회 화면 — 로케이션에서 상품 상태까지

편집 화면과 별개로, 현장에서 쓰는 조회 화면이 있다.
검색하면 로케이션 문자열 대신 셀이 하이라이트된다. 다만 현장 질문은 좌표에서 끝나지 않는다.
그 칸에 뭐가 있는지, 그 상품이 지금 어떤 상태인지를 이어서 봐야 한다.

### 8-1. 셀에서 상품까지

클릭은 이 순서로 내려간다.

```text
셀 클릭   → 그 칸의 설비 카드 (행거 / 경량 렉 / 렉 / 존)
카드 클릭 → 그 로케이션의 상품 목록
상품 클릭 → 상품 상세 + 상태 로그
```

한 셀에 매핑이 여러 개면 카드도 여러 장이다. 경량 렉 2층·3층이 같은 좌표에 있으면 층마다 카드가 나온다.
3절에서 공간과 설비를 나눈 이유가 여기다. `object_id` 한 칸이었으면 카드가 한 장으로 뭉개진다.

상품 상세의 타임라인은 새로 만들지 않았다. 이미 쌓여 있던 `goodsLogisStateLog`를 붙였다.
맵이 답하는 건 위치고, 상태가 필요하면 있는 이력을 쓰는 쪽이 맞았다.

### 8-2. 위치가 없는 검색

맵 조회의 빈 결과는 "상품이 없다"가 아니다.
아직 입고 전이거나 이미 출고된 경우가 많아서, 빈 배열을 그대로 돌려주면
작업자는 같은 번호를 다른 메뉴에 다시 넣는다.

그래서 0건이면 상품번호는 상세·상태 로그로, RFID는 이력 조회로 보낸다.
위치 테이블에 행이 없는 것과 상품이 없는 것을 같은 응답으로 두지 않은 것이다.

결과가 현재 층에 없으면 그 층으로 옮긴다. 여러 층에 흩어져 있으면 가장 낮은 층부터 보여준다.
결과가 하나뿐이면 그 셀까지 열어서, 검색한 상품이 든 매핑을 펼친다.
화면에서 다시 고르게 두지 않고, 이미 가진 좌표와 매핑으로 닫는다.

## 9. 그래서 다음은 경로 탐색이다

지금 구조는 경로 탐색용 그래프의 입력 데이터까지다.
실제로 BFS를 돌리는 코드는 아직 없다.

하지만 붙이는 데 필요한 건 다 있다.

```text
노드   : (warehouseId, floor, pointX, pointY) 중 걸어갈 수 있는 타입만
         → FLOOR / DOOR / STAIRS
엣지   : 이웃 노드가 존재하는 상하좌우
접근   : 랙·행거 셀은 노드가 아니라 목표다.
         인접 통로 셀에서 availableDir이 가리키는 쪽으로만 닿는다
```

통행 가능한 타입만 세면 격자 3,872칸 중 1층 1,001칸, 2층 619칸이 노드가 된다.
한 층 1,000개 남짓이라 맵 한 장을 읽으면 그래프가 통째로 메모리에 올라온다.
그리고 2층에는 `DOOR`가 하나도 없다. 진입로가 계단 12칸뿐이라 층을 넘는 동선은 그 12칸을 반드시 지난다.

여기서 4절의 구분을 조심해야 한다. `availableDir`은 **통행이 아니라 접근 방향**이다.
`2`인 행거 셀을 걸어갈 수 있는 칸으로 취급하면 작업자가 행거를 통과하는 경로가 나온다.
비트 하나로 둘을 다 표현하려다가 여기서 헷갈려서, 걸을 수 있는지는 타입이 답하고
어디서 집을 수 있는지는 비트가 답하도록 역할을 갈라놨다.

목표는 피킹 리스트에 담긴 여러 로케이션을 놓고

1. 각 로케이션을 셀 좌표로 변환하고
2. BFS로 구간 최단 거리를 구한 뒤
3. nearest-neighbor로 방문 순서를 근사해서
4. 작업자의 불필요한 왕복을 줄이는 것

이다.

### 여기서 멈춘 이유, 그리고 다시 여는 이유

여기까지가 회사에서 구현한 범위다.
바로 이어서 경로 탐색에 들어갈 생각이었는데, 회사 사정으로 개발자를 한 명만 남기게 되면서
정리하고 나오게 됐다. 이 글도 그만둔 뒤에 쓰고 있다.

그래서 이 기능은 검증할 기회를 놓쳤다.
"동선을 계산해줬더니 작업자가 실제로 덜 걸었는가"는 현장에서만 확인되는 값인데,
이제 그 현장에 접근할 수 없다. 이게 가장 아쉽다.
격자로 잡은 이유가 전부 다음 단계에 걸려 있었기 때문이다.

그런데 손을 놓고 나서도 궁금증이 남았다.

- 격자 2,000셀에서 나온 통행 노드 1,000개로 BFS를 돌리면 체감 속도가 어떨까
- 2층 진입로가 계단 12칸뿐인 구조에서 층을 넘는 경로는 어떻게 갈라질까
- nearest-neighbor로 근사한 순서가 최적해와 얼마나 벌어질까

머릿속에서 설계만 해둔 것과, 실제로 붙여보고 깨지는 걸 보는 건 다르다.
그래서 운영 DB를 복사한 로컬 사본에 나머지를 직접 붙여보려고 한다.
현장 효율은 증명할 수 없지만, **이동 거리는 맵 데이터만으로 계산된다.**
같은 피킹 리스트를 로케이션 ID 순서대로 도는 경우와 계산된 순서로 도는 경우의
이동 셀 수를 비교하면, 최소한 알고리즘이 무엇을 줄였는지는 숫자로 말할 수 있다.

창고를 코드 목록이 아니라 좌표와 방향을 가진 격자로 정의한 것,
그게 이 기능에서 제일 중요한 결정이었다고 생각한다.
그 판단이 실제로 값을 했는지는 아직 확인하지 못했고, 그래서 남은 걸 마저 만들어보려고 한다.

다음 글에서는 여기에 BFS를 얹어, 맵 위에 실제 동선을 그려볼 예정이다.
운영에서 못 돌려본 기능이 로컬에서 어디까지 서는지, 그 과정에서 무엇이 걸리는지를 적게 될 것 같다.

### 정리

| 문제 | 선택 | 결과 |
|------|------|------|
| 로케이션 ID를 사람이 못 읽음 | `(x, y, floor)` 격자로 시각화 | 3,872셀을 두 층으로 렌더 |
| 벽/통로를 타입으로 표현하기 어려움 | `availableDir` Bit Flag 1컬럼 | 타입 enum 9개 고정, 조합 16가지 |
| 엣지 테이블의 유지 비용 | 셀 속성으로 엣지 저장 | 행/열 삽입 시 엣지 재계산 0회 |
| 레이아웃이 계속 바뀜 | JPQL 벌크 shift + 행/열 삽입 | 좌표 이동이 UPDATE 1회 |
| 설비마다 ID 체계가 다름 | enum에 증가/층 인덱스 상수화 | ID 생성부 타입 분기 0개 |
| 셀 3,800개를 손으로 못 찍음 | Set 선택 + Shift 범위 + 일괄 API | 3,274개 매핑을 범위 선택으로 투입 |
| 검색 결과가 빈 배열 | 위치 없음과 상품 없음을 같은 응답으로 두지 않음 | 상세·이력 조회로 보냄 |
| 위치를 찾은 다음이 비어 있음 | 셀 → 설비 카드 → 상품 → 기존 상태 로그 | 타임라인을 새로 만들지 않음 |

표에 피킹 효율은 넣지 않았다. 넣고 싶었는데 넣을 숫자가 없었다.
센터의 피킹 기준은 시간당 100개 정도이고 그 숫자를 움직이는 건 결국 동선인데,
이 글에서는 아직 동선을 계산하지 않는다. 시간당 처리량은 다음 글의 BFS가 건드릴 값이다.

대신 맵이 실제로 실무에 도움을 준 것은 **단건 조회**였다.
